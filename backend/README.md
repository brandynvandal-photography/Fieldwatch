# Fieldwatch backend

Node 20, Express, SQLite. Watches the National Weather Service for every festival in its window, stores alerts, and pushes new ones to subscribed phones. No user accounts anywhere; phones register only an APNs token and a festival id.

## Run it

```
npm install
npm start                   # seeds data/festivals.json into an empty database and prints the admin key once
npm test                    # every route, with api.weather.gov replaced by a fixture
```

Nothing to configure. `.env.example` lists every variable, all optional; copy it to `.env` to change one (picked up automatically on Node 20.12+, anything already in the environment wins). The admin key and the web push keys are made on the first boot and kept in the database; the services we read see `Fieldwatch/<version> (+the site address)`, a contact they accept. Then point the iOS app at it: set `FieldwatchBackendURL` in `project.yml`.

`src/server.js` only listens and starts the poller. The routes are in `src/app.js`, which the tests import directly.

Admin calls send the admin key (`ADMIN_KEY`, or the one the server made on first boot) as `x-admin-key`. A festival's safety team sends its own staff key in the same header: it works for that festival's posts, report moderation, ground and record (`PUT /festivals/:id`), and for nothing admin-wide. Keys are kept as hashes and shown once. Errors are always JSON (`{ error }`), including malformed bodies and unknown paths. Staff posts take an optional `severity` (`unknown`, `minor`, `moderate`, `severe`, `extreme`; default `minor`) that maps onto the same scale as NWS alerts.

Post a staff update:

```
curl -X POST localhost:3000/festivals/dusk-ridge-2026/posts \
  -H 'content-type: application/json' -H 'x-admin-key: change-me' \
  -d '{"title":"Medical tent has moved","body":"Now beside the water station at the east gate."}'
```

## How the alert pipeline works

1. `poller.js` runs every `POLL_SECONDS` (30; the weather service caches its answers about that long, so faster buys nothing), `POLL_CONCURRENCY` (3) festivals at a time; a pass still running when the next is due is skipped and counted (`/health` → `polling.overruns`). Every weather service call gives up after `NWS_TIMEOUT_MS` (10 s) and a timeout or a 5xx is tried once more (`polling.nws.retries`). A festival is "in window" from a week before it starts (or `groundsOpen`) to 1 day after it ends. An alert the service stops listing is ended only when it is missing from two polls in a row, or when a newer message says it replaces it: the service answers empty for seconds at a time and one empty answer is not an end. Alerts are stored per festival (`alerts` is keyed by festival and id), so one warning across two festivals' grounds ends at each on its own.
2. For each, it asks for the alerts of the festival's county and forecast zone (`alerts/active?zone=FLC121,FLZ024`, the two zone ids `/points` names; `nws.js` `alertsFor`) and keeps the ones that reach the grounds: an alert drawn as a polygon counts when the polygon comes within about a mile of the coordinate (`reaches`), an alert with no polygon is zone-wide and always counts. That is what a point query (`?point=lat,lon`) misses: a warning polygon drawn across the edge of a large site, or ending a few hundred meters from the pin. When the zones are unknown it falls back to the point query. The service lists a warning once per update it has sent and once per zone segment, and a county query brings in every segment in the county, so `condense` keeps one message per warning: an update replaces what it references (the poller stores it and ends the old message without pushing again, by `replaces`), a zone-wide segment counts only where it names the grounds' own zone, county or fire zone, and one event with one end is listed once, the newest. Either way the GeoJSON is normalized into the same `SafetyAlert` shape the app uses.
3. New alert ids get stored and pushed. Alerts NWS stops listing get an `expiresAt` of now, so phones drop them on their next refresh.
4. The push payload carries the full alert as JSON, so a tapped notification opens the detail screen even with no network.
5. Every 20 minutes it also reads each live festival's hourly forecast and grid (`incoming.js`). When the next twelve hours turn stormy (thunder 30%+), windy (gusts 35 mph+), wet (rain 60%+) or dangerously hot (heat index 100+) and the start is within `HEADS_UP_HOURS` (default 3), it stores a heads-up of its own (`channel: "headsup"`, severity moderate, `onset` = when it starts, expires when the window ends) and pushes it once per window: "Storms expected around 5:00 PM", then what to do with the time there is and where to shelter. A watch or warning NWS already issued for the same thing is left to speak for itself. NWS never lists our heads-ups, so the poller does not end them; they end with the window. The model also reads the grid's feels-like and wind direction: a cold night (feels-like at or under 40°) and rain hard enough to flood (half an inch in an hour, an inch over three, a third of an inch onto low ground) are windows of their own, a wind heads-up names the side the wind comes from and says `maybe past` a line a gust is only just over (`gustOdds`), a second window later in the twelve hours rides along as `next`, and a window that comes while people sleep gets the before-you-turn-in line. The stored heads-up follows the forecast when its window moves (same id, `updatedAt`, no second push, the page told on the stream) and is withdrawn (`withdrawn: true`, ended) when the forecast lets go of it.

The phone also polls `/alerts` when it's open, and falls back to NWS directly if this server is down. Its answer carries `codes`, the lightning code of every festival that is on by id, alerts or not, so the home page shows a code beside every name.

Everything that changes is announced on the **live stream** (`live.js`): `changed(festivalId, kind)` is called when an alert lands or ends (`alerts`), a heads-up is stored (`headsup`), new radar frames land (`radar`), a lightning code or nearest flash changes (`lightning`), a staff post goes out (`posts`) or the ground is reported (`ground`), and every open `GET /events` connection gets the event (a comment ping every 25 s keeps proxies from closing it; the browser reconnects on its own after 5 s). The web build opens one on load and refreshes just the festival or the feed named, so an open page moves within a second of the backend instead of waiting for its own poll. The stream has run only against the test client so far, not through Railway's proxy.

## Festival data

Known grounds live in `data/grounds.json`: the places festivals happen, each with the pin on the grounds, the county, whether people camp, whether it is a building, a source, and `verifiedOn` (null until someone has dropped the pin on a map). An import or a suggestion within a kilometer of known grounds, or within three kilometers when its venue names them, takes the grounds' pin, name, county, camping and roof (`src/grounds.js`), so a ticket site's box-office pin lands on the field. Staff move a pin from the Ground screen (Pin it here) with `PUT /festivals/:id`.

Several sources feed one table, and every record passes through `normalizeFestival` in `src/festivals.js` on the way in:

- **Curated** (`data/festivals.json`): the featured list, hand-checked against each festival's own site, seeded on first boot and re-applied by `npm run seed`. Coordinates need to be the actual grounds, not the town: NWS alerts are polygon-based. These are the bubbles in the picker.
- **Ticketmaster** (`src/importers/ticketmaster.js`, needs `TICKETMASTER_KEY`, free at developer.ticketmaster.com): a daily walk through the next twelve months of US music listings, three nets: anything with "festival" in its text, anything Ticketmaster itself styles a festival (plus any listing with four or more acts), and everything Front Gate sells, which counts as a festival without a name check because Front Gate sells festivals and little else. The first two nets span every source behind the API, Universe included, which is where small self-serve festivals turn up. The report counts listings per ticket site (`hosts`) so the first real run shows what each net caught. Per-day and multi-day-pass listings fold into one festival; parking and camping add-ons are dropped, and so are the late-night shows and aftershows a festival sells under its own name in clubs across town; and a listing that matches a festival from another source (same grounds on overlapping dates, or the same name within 8 km, a nickname included: ACL Fest is Austin City Limits, Lolla is Lollapalooza) is skipped, so a curated record is never overwritten by a ticket page. A listing that vanishes before it starts is treated as canceled and removed; imports that ended a month ago are pruned; and a stored import that a source ahead of it in the run order holds (a curated record, an approved suggestion, a feed, then Ticketmaster, SeatGeek, Edmtrain, Wikidata) is removed on its source's next run, so a duplicate the matcher has since learned to see never needs hiding by hand. Around a hundred calls a run.
- **SeatGeek** (`src/importers/seatgeek.js`, needs `SEATGEEK_CLIENT_ID`, free at seatgeek.com/account/develop): every upcoming US listing in SeatGeek's `music_festival` taxonomy, folded the same way. Reaches a lot of ticketing Ticketmaster does not carry, including smaller independents. A few calls a run.
- **Edmtrain** (`src/importers/edmtrain.js`, needs `EDMTRAIN_KEY` from edmtrain.com/developer-api): every upcoming US festival on Edmtrain in one request, the electronic side of the calendar. Their API terms are honored in the data model: each event's link is stored as the record's `source` and shown as given, the data is never resold, and the key stays on the server.
- **Wikidata** (`src/importers/wikidata.js`, no key, on by default; `WIKIDATA_IMPORT=false`, `0` or `no` turns it off; it runs from the first boot, since the User-Agent it sends names the app's page): every US festival on Wikidata with coordinates and an official website, from two SPARQL queries (every kind of festival, then the US instances of those kinds a few hundred kinds at a time, not dissolved; two items sharing a site count once, the lower id). Wikidata rarely knows this year's dates, so the importer reads each festival's own homepage for the schema.org JSON-LD sites publish for search engines (`Festival`, `MusicEvent`, `Event`, `@graph` included; canceled, postponed and moved-online blocks skipped) and takes the dates from there: per-day blocks of one name fold into one festival, only the first two weeks a page announces counts (so this autumn's edition does not run into next spring's), an edition more than a year out is ignored, and the page's coordinates are used when they are within 50 km of Wikidata's, else Wikidata's. It is a polite crawler: robots.txt is honored (the group naming our product token, else `*`; wildcards and `$` as written; a 5xx robots.txt is an error for that site, not permission), redirects are followed by hand (five at most, robots.txt read again on every new origin), nothing but a public DNS name is ever fetched (no IP literals, localhost or `.local`), at most `WIKIDATA_MAX_SITES` (250) sites a run with `WIKIDATA_PAUSE_MS` (400) between them, sites never seen first and then the ones checked longest ago, 8 s and 1 MB per page, and each site's result is kept in the settings table (`wikidata:sites`) for `WIKIDATA_CACHE_DAYS` (6), so a daily run only reads sites it has not seen lately. Ids carry the item (`wd-q123-riverfest-2026`), the site is the record's `source` and `website`, the item id is kept as `wikidata`, and a bad site keeps what it said last time and counts as an error without stopping the run or holding back pruning; only a failed query does that.
- **What stays out** (`src/names.js`): names come down to the festival (no day, pass, lineup, age note or year, so "Rock The South - Thursday - with Zach Top" folds into Rock The South); SeatGeek listings need a festival word in the name, a performer that is the festival, the placeholder start time a multi-day event gets, or three acts on the bill; tours, tributes and concerts without "fest" in the name, canceled shows, kick-off shows, afterparties and car registration are dropped; anything outside the National Weather Service area is refused everywhere. Two records within 8 km on overlapping dates with the same core name are one festival. Staff hide the rest from the app's All festivals screen.
- **Feeds** (`src/importers/feeds.js`, `FESTIVAL_FEEDS`): your own CSV or JSON, anywhere that serves a file, for example a Google Sheet published to the web as CSV. Columns can be sheet-style (`Festival, Where, Lat, Lon, First day, Last day, Website`); a bare date means the whole day. Rows are trusted, so this is how a maintainer edits the list from a phone.
- **Community** (`POST /festivals`): the small independent ones no feed knows about. Anyone can send a name, a place and dates from the web build; it sits in the moderation queue until an admin approves it there. Nothing a stranger sends becomes a partner feed or a site map.

On Railway, attach a Volume to the service (service menu, Attach Volume; any mount path). The backend sees `RAILWAY_VOLUME_MOUNT_PATH` and keeps the database, radar frames and clips there, so a redeploy keeps the push keys, subscriptions, admin edits and reports. Without one, every deploy starts empty: the festival list re-imports itself, and phones that had warnings on register again, quietly, the next time the app opens (`POST /push/subscribe` with `quiet: true`).

Imports run at boot and every `IMPORT_HOURS` (24) when a source is configured, or on demand with `POST /admin/import` or `node src/importers/index.js`. They run widest first (Ticketmaster, SeatGeek, Edmtrain, Wikidata, feeds), and a festival that several sites list is kept once, from the first that listed it. The shared folding and write path is `src/importers/common.js`.

**What is listed.** `GET /festivals` returns only festivals that are on: from the grounds opening until the day after the end. Grounds open `LEAD_DAYS` (7) before gates for early entry, vendors and build crews, or on the record's own `groundsOpen` date when it has one. There is no point in a platform for alerts about a place nobody is at yet. The same window decides which festivals the poller watches and the radar loop pre-fetches (only featured ones and any a phone asked about in the last day; the rest fetch on request).

`feeds` holds public audio streams you have permission to relay. Broadcastify is not licensing new scanner apps, so leave this empty unless a feed owner has agreed.

## Deploying

One Node process with a disk. Run a single instance: the poller and the radar loop are not built to coordinate across several. The `Dockerfile` here is what hosts build from, and an empty database seeds itself from `data/festivals.json` on first boot, so there is no separate seed step.

### Railway, from a phone

1. railway.com, New Project, Deploy from GitHub repo, pick `Fieldwatch`.
2. Service, Settings, Source: set Root Directory to `backend`. Railway finds the Dockerfile there. (If it is left unset, the `Dockerfile` at the repository root builds the same image, so a build never falls back to Railpack and fails on the root folder.)
3. Add a Volume to the project and attach it to the service with mount path `/data`.
4. That is the setup. Nothing in Variables is required: the database, radar frames and clips follow the volume (Railway announces its mount path), the admin key and the web push keys are made on the first boot, the proxy hop is trusted, and the services we read see `Fieldwatch/<version> (+the site address)`. Open Deployments, the first deploy's log, and copy the admin key from the line that says it is shown once; it goes in the web build's Settings (`?staff=1`). Optional, in the Raw Editor: `NWS_USER_AGENT=Fieldwatch (a mailbox you read)` to give the weather service a mailbox instead of the site; `TICKETMASTER_KEY`, `SEATGEEK_CLIENT_ID` and `EDMTRAIN_KEY` for festival sources beside Wikidata and the festival sites; `NODE_KEY` once a receiver node exists; `CORS_ORIGIN` narrowed to the web build's origin (for GitHub Pages, `https://<user>.github.io`) once you are done trying it from other places. The API sets no cookies, so `*` is safe. Railway sets `PORT` itself.
5. Settings, Networking, Generate Domain. Open `https://<that domain>/health` and you should see `{"ok":true,...}`, `adminKey: "database"` and the `userAgent` it goes by.
6. The web build already points at `https://fieldwatch-production.up.railway.app` (`DEFAULT_BACKEND` in `web/index.html`, and `FieldwatchBackendURL` in `ios/project.yml`). Another deployment's domain goes in the web build's Settings, or in those two places.

Deploys again on every push to `main` that touches `backend/`.

### Elsewhere

- Fly.io: `fly launch` inside `backend/`, `fly volumes create data`, mount it at `/data`, same variables. Needs the CLI, so a computer.
- Render: works with the same Dockerfile and a disk at `/data`, but the free tier sleeps between requests and the poller sleeps with it. Use a paid instance.
- A VPS: `npm ci --omit=dev`, `node src/server.js` under systemd, nginx in front with `TRUST_PROXY=1` (the one variable a proxy needs); `.env` from `.env.example` only to change something.

Push is optional everywhere: leave the `APNS_*` lines out until there is a key, and the server starts without them (alerts are stored and served, just not pushed).

**Web push** (warnings on a phone's Home Screen, no app store) needs nothing: the server makes a VAPID key pair on first boot and keeps it in the database on the volume. To bring your own pair, run `npm run vapid` and set `VAPID_PUBLIC_KEY` and `VAPID_PRIVATE_KEY`; set `SITE_URL` if the web build does not live at the GitHub Pages address. A subscription made against an earlier pair is dropped on the next send and the phone switches warnings on again. From then on every new warning, watch and staff post reaches every browser that switched warnings on for that festival; advisories are not pushed. A browser that follows a point instead of a festival is polled the same way: the poller asks the weather service about every distinct point (rounded to about a kilometer) that some phone follows. Dead subscriptions are dropped on the next send. The switch is in the web build's home screen; on an iPhone it works once the site is on the Home Screen (iOS 16.4+).

## Radar

`radar.js` keeps a 12-hour loop of NEXRAD base reflectivity per festival: one 512 px PNG per `RADAR_STEP_MINUTES` for a 320 km Web Mercator square around the grounds, fetched from the Iowa Environmental Mesonet WMS-T archive (`RADAR_WMS`, no key) and stored under `RADAR_DIR/<festivalId>/<timestamp>.png`. A frame never changes once it exists, so only the newest is ever fetched, the oldest is pruned as the window moves, and every phone gets the same files from this server instead of hitting the archive. Festivals in their window refresh every `RADAR_REFRESH_SECONDS`; a request for `/radar` or `/pack` kicks off a refresh in the background if one is due and answers with what is on disk. A frame the archive won't produce is retried three times and then left out.

The manifest (also inside the pack as `radar`) mirrors `RadarLoop` in Swift: `bounds` in degrees, `frames` oldest first with relative URLs, `attribution` that the app must display. Newest frame is at least ten minutes old; that is how long the composite takes to land.

## Lightning

`lightning.js` grades lightning at every festival that is on from the GOES-R Geostationary Lightning Mapper. NOAA publishes every 20-second flash file (`GLM-L2-LCFA`) on public S3 buckets (`GLM_BUCKETS`, default `noaa-goes19,noaa-goes18`: GOES-East and GOES-West, no key, no signing) a minute or two after the fact. Every `LIGHTNING_SECONDS` (20, the cadence the files land at) the server lists the current hour on each bucket, fetches the files it has not seen (newest first, 30 at most per pass), reads `flash_lat`, `flash_lon` and `flash_time_offset_of_first_event` with h5wasm (NetCDF-4 is HDF5; no native build), keeps the flashes within 40 miles of a live festival for 30 minutes, and grades on the festival safety protocol: **red** a flash within 8 miles in the last 30 minutes (rapid evacuation, full work stoppage; all clear 30 minutes after the last one, and stale data never clears a red), **orange** nearest flash in the last 15 minutes 8 to 12 miles out (execute evacuation procedures, staff hold posts to assist attendees), **yellow** 12 to 20 (pay attention, prepare for orange and a work stoppage), **green** nothing within 20 miles in the last 15 minutes, **none** no data in the last 10 minutes. Files 5 to 10 minutes late hold the last code, marked `held` with `dataAgeSeconds`, rather than flipping to no data and back; a red at its all-clear with late files holds up to 10 more minutes with `allClearHeld` while the all-clear waits for data, and after that it is no data, never a green nobody confirmed. A change to orange or red is stored and pushed as an alert in the protocol's own words (`PROTOCOL` in `lightning.js`; `channel: "lightning"`, `code`, id `lightning-<festival>-<code>-<minute>`): red is severe and its `expiresAt` moves out with every new flash within 8 miles; orange is moderate and ends fifteen minutes after the last flash within 12 miles, or the moment the code changes. After a restart an alert already in the database is adopted, not pushed again, and while the files are read again (newest first, thirty a pass) it keeps the grade at its code until its own end, so `/festivals/:id/lightning` never says green under a red alert that is still out. Indoor events (see Ground) are not graded: `code` is `indoor` and no alert goes out. `GET /festivals/:id/lightning` returns the grade (also in the pack as `lightning` and on each `/alerts` item; `motion` says where the flashes are going: heading, speed, closing and the minutes until they would be here at that rate, from the last ten minutes against the ten before, `motionOf`), `GET /point/:lat,:lon/lightning` and `/point/:lat,:lon/lightning/flashes` the same for a spot a phone stands on (asking keeps the spot in the reader's reach for a day and the reader runs for it with no festival on; the first fifteen minutes answer `warming: true`, since a green nobody could see would be a lie; no alert and no push for a spot), `/health` has `lightning` with per-bucket counts and the last error. Nothing runs while no festival is on; `LIGHTNING=false` turns it off. The mapper sees cloud tops at about 8 km and misses some flashes under a thick anvil, so the app says the festival's own lightning vendor is the authority.

## Ground

`ground.js` gives the rain advice something to stand on. For a festival that is on, once, it looks up the surface under the coordinate (OpenStreetMap, one Overpass `is_in` query: a surface tag, then a use such as a park or a parking lot, then land cover; boundaries say nothing; when nothing under the point says, a second query takes the nearest mapped ground within 250 m, a field whose outline stops short of the pin or the lot beside it, and names the distance; and when OpenStreetMap has nothing at all, the National Land Cover Database's 30 m cell at the point from MRLC's map service, `NLCD_URL` and `NLCD_LAYER`: pasture and grassland are grass, crops and forest dirt, developed land paved or mixed, wetlands low ground, water says nothing) and the soil (the USDA soil survey's map unit at the point: hydrologic group A to D, drainage class, a dual group read as its wetter letter, poorly drained meaning low ground), and writes them onto the festival record as `ground`. A lookup that found no surface or no soil, or hit an error, is tried again after a day, so a service that was down does not leave a festival on assumptions for its whole run. Every three hours it reads the rain of the last two days at the point from the Iowa Mesonet's daily analysis (`IEMRE_URL`). Staff can set what the lookups cannot see with `PUT /festivals/:id/ground` (`surface`, `soil`, `low`, `structures` among canopies, inflatables and stage, a `note`), run the lookups again with `POST /festivals/:id/ground/lookup`, or clear the override with `DELETE`; an edit or an import keeps `ground`. `GET /festivals/:id/ground` (also in the pack as `ground`) is what the model reads: the override over the lookups over the defaults (trampled grass on average soil, canopies standing), each with its source, plus `past` rain.

The model (`incoming.js`, the shared block) turns that into a **mud tier**: effective rain is what is ahead plus six tenths of yesterday's and three tenths of the day before's, against a threshold by soil (A 1.5 in, B 0.75, C 0.5, D 0.3) and surface (bare dirt sooner, gravel later); over it is *soft*, over twice it is *deep*, an inch or a hard rate on low ground is *water*; blacktop never makes mud but turns *slick* at a tenth of an inch and *runs off* at an inch or a hard rate; sand only puddles. Each tier has its own list, and the list follows who is asking: someone **camping** (tents, canopies, the car call), a **day visitor** in a lot with no in and out (the walk, the phone, leave before or wait it out), or **crew** (the booth, the stage, work and rest by the flag). Whether the event is **indoors** comes from the record's `indoor` (staff on the Ground screen; a building, a club, a hall or an arena under the coordinate in OpenStreetMap; else the venue's own words in the listing, a nightclub or a ballroom against a park or fairgrounds, the building's word winning; unknown counts as outdoors, the safe side). Indoors needs every source that speaks to agree: mapped open ground under the pin, a park, a farm or a mountain in the listing, or people camping here (a campground under the pin, a camping pass, the seed) each say outdoors and beat a building under the pin, since an imported pin often sits on the lodge or the box office of grounds open to the sky; a stadium, a grandstand, a pavilion, an amphitheater or an events venue with no building is no roof either. Staff keep the last word. Indoors the building is the shelter: no lightning code and no code alert (`/festivals/:id/lightning` says `indoor`), no wind, heat or rain heads-up, and a storm or flood heads-up carries the inside-is-shelter line and one short list for everyone. Whether people camp at a festival comes from the record's `camping` (set on the seed; staff on the Ground screen; a campground under the coordinate in OpenStreetMap; a camping, RV or glamping pass on sale beside the festival at Ticketmaster or SeatGeek), and where nobody knows, the day visitor's list is used, so tent advice never reaches a festival without tents. The push uses the festival's default; the app asks each phone once ("I'm camping", "Day visitor", "Crew or vendor") and redoes the list. The car is never told to move to hard ground as if it could: campers hear "if the car can still move, move it now; if not, plan to leave after the ground dries", day visitors hear "the lot will be slow: leave before it starts, or wait it out". Every task has a length, so the heads-up works a start-by time back from the arrival ("Move the car to hard ground by 4:45 PM"), the longest task first; past its time it says now. The push carries the first deadline, the forecast and the mud sentence, whole sentences up to its limit; the alert carries the whole plan. **Wind** is judged against what the record says is standing (`structures`): inflatables come down at 20 mph gusts, pop-up canopies fail around 30, stages and rigging hold to 40; the lowest line among them is the wind hazard's threshold, the push names the lines crossed ("gusts to 38 mph past the canopy line"), and a stage or inflatables past their line put their own task at the top of the list. **Reports from the field** close the loop: `POST /festivals/:id/ground/report` with a `state` of fine, soft, mud or water (five per phone per ten minutes) stores the report with the rain the model counts at that moment; the least rain at which anyone reported the ground soft, nudged past any report of fine ground at more, becomes the venue's learned threshold (`ground.learned` on the record, sixty days of reports), which beats the soil table from then on. `GET /festivals/:id/ground` and the pack carry `reports` (the last one, and how many in six hours). **Heat** is judged two ways: the heat index (a shade number for someone at rest, 100°F) and an estimated wet-bulb globe temperature from the grid's air temperature, humidity, wind and cloud (Stull's wet bulb, a globe warmed by the sun less cloud and wind, the 0.7/0.2/0.1 blend), which earns a flag: green under 82°F, yellow to 85, red to 88, black above, each with work-rest guidance for crews and anyone dancing. Red or black is a heat hazard on its own; the push names the flag and the alert carries the guidance.

## Nowcast

`nowcast.js` reads the newest three radar frames already on disk for a festival (radar.js keeps a 512 px square every ten minutes, 625 m per pixel, the grounds at the center), turns each into an echo mask at 128 cells (a cell is echo when a quarter of its pixels are colored; the archive draws rain in color on transparent, borders in gray), finds the shift that lines two masks up best (the storm motion over a step, searched to 120 km/h), walks upstream from the center along that motion to the first echo, and divides by the speed. `GET /festivals/:id/nowcast` (also in the pack as `nowcast`) has `minutes` until it arrives (0 when it is raining on the grounds, null when nothing is coming this way), `speedKmh`, `heading`, `distanceKm`, `ageMinutes` (the newest frame is always some minutes old) and `tracked`. Inside two hours it moves a heads-up window's start earlier, or is a window of its own ("Rain on the radar, about 40 min out") when the forecast has none; beyond that the forecast rules. It only exists for festivals whose frames are kept (featured, or opened on a phone in the last day). Proven on frames drawn by hand; never run on real ones. Nothing here has run against the live services yet; `/health` has `ground` and a record's `ground.lookupError` says what failed.

## Incidents

Scanner traffic and attendee reports, filtered down to hazards.

| Method | Path | Auth | What it does |
|---|---|---|---|
| GET | `/festivals/:id/incidents` | none | Published incidents from the last 48 hours |
| POST | `/festivals/:id/incidents` | `x-node-key` | A receiver node uploads one radio call (multipart: `audio`, `transcript`, `talkgroup`, `occurredAt`, `id`) |
| POST | `/festivals/:id/reports` | none | Attendee report, goes to the moderation queue, 5 attempts per 10 minutes per IP |
| GET | `/festivals/:id/incidents/pending` | admin | Moderation queue |
| POST | `/festivals/:id/incidents/:iid/publish` | admin | Publish (optionally with an edited `summary`), pushes to subscribers |
| DELETE | `/festivals/:id/incidents/:iid` | admin | Remove |
| GET | `/audio/:file` | none | The clip |

`incidents.js` holds the category rules. A call that matches none of them is dropped, audio and all. Phone numbers, plate-shaped tokens and name phrases are redacted before storage. `INCIDENT_AUTO_PUBLISH=false` sends scanner incidents to the queue too. A node's own incident id is kept when it sends one, so a phone that already saw the incident on the node's Wi-Fi doesn't get a duplicate; a re-upload of a known id is acknowledged and its audio discarded.

The rules are duplicated in `node/uploader.py`. `test/fixtures/hazard-samples.json` is run through both, so they can't drift silently.

If a node couldn't transcribe on-device, set `OPENAI_API_KEY` and the backend will run Whisper on the upload.

## Operating it

- **Watch `/health?strict=1`** from an uptime monitor (UptimeRobot, Better Stack, a cron with curl): it answers 503 while a festival is on and the alert poll has not succeeded in ten minutes or no lightning file has been read in five. The plain `/health` always answers 200 and says the same in `problems` and `warnings`.
- **Backups**: a copy of the database is written once a day (`BACKUP_HOURS`) to `BACKUP_DIR` (default: a `backups` folder beside the database, on the volume), the last `BACKUP_KEEP` (7) kept. `GET /admin/backup` downloads the newest; `POST /admin/backup` takes one now. Restoring is copying the file over `DB_PATH` with the service stopped.
- **Counters**: `GET /admin/stats` counts use per festival per day: packs opened, alert lists served, alerts stored and how long after issue, pushes sent (web and APNs), heads-ups, posts, hazard reports, ground reports, follows. Nothing in them names a phone, an address or a person, in keeping with the no-tracking rule; they are kept ninety days.
- **The admin key**: `ADMIN_KEY` if set; otherwise made on the first boot, kept hashed in the database and printed once, in that boot's log. Lost it: set `ADMIN_KEY` (the environment wins), or `railway run npm run admin-key` to make another, which the running server takes on its next request. `/health` says which it is (`adminKey`: environment or database) and never the key.
- **Holds and notices**: `POST /festivals/:id/posts` takes a `kind` (`notice`, `shelter`, `evacuate`, `pause`, `allclear`) and, for a hold, `minutes` (60 unless said, 720 at most); shelter and evacuate are always severe, a hold is kept with the alerts until its end so the festival page carries it, and the all-clear ends every hold standing. The reach of every post (phones pushed) is kept on it; `DELETE /festivals/:id/posts/:pid` takes a post back, ends its hold and tells the phones quietly under the same tag. A report landing is announced on the stream (`reports`) for the staff's queue. `POST /festivals/:id/partner-key` answers with `handoff`, a link with the key in it, and `qr`, that link as an SVG to scan once per staff phone; the record carries `shelter` and `medical` in the team's words (`PUT /festivals/:id`), and a hold's `instruction` names the shelter.
- **Pushes act, and say when it is over**: a warning's push opens with the line to act on and the line of what not to do, in the festival's own setup (`actionLines`, shared with the web build in `incoming.js`), then the festival and the headline. A warning that drops out of the listing twice running, with nothing of its kind still standing, goes out again quietly as `Ended: …` under the same tag (`pushEnded` in `webpush.js` and `push.js`), with what to do now; a Code Red or Orange that lifts does the same in the protocol's words (`liftWords`), including when the mapper went quiet and could not confirm it.
- **Pushes carry their end**: a web push goes out with a `TTL` of the alert's time left (five minutes at least, six hours at most) and an APNs push with the same `expiry` and the alert id as `collapseId`, so a phone that was out of signal is never handed a warning that ended hours ago; the web payload says `expiresAt` and `issuedAt` and the service worker shows a late one as ended. The payload stays under the 4 KB push services allow: the alert rides along with its text cut to the first sentences and no geometry (`webpush.js` `slim`, `fit`).
- **Who we are**: every service read (the weather service, the radar archive, the lightning buckets, the ground lookups, Wikidata, the festival sites) is free and keyless, and sees `Fieldwatch/<version> (+the site address)` unless `NWS_USER_AGENT` names a mailbox; `/health` shows it as `userAgent`.
- **The shakedown script**: `node scripts/shakedown.mjs https://your-host ADMIN_KEY` reads the whole backend in one pass from any machine and prints what is live, stale or failing. `docs/shakedown.md` is the checklist for the first live weekend.
