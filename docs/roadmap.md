# Roadmap

Priority order. Each item is sized for one Claude Code session.

1. **Compile the iOS app.** `xcodegen generate`, build, fix errors. A no-Xcode session already fixed what it could find by reading: `SWIFT_VERSION` was `5.9` (not a language mode; now `5.0`), `RelayService`'s `lazy var`s and off-main bookkeeping are `@ObservationIgnored`, `NodeDiscovery`'s browser and probe likewise, `AppDelegate` registers for push on the main actor, and `NSAllowsLocalNetworking` is set so `http://localhost:3000` and a node's `http://` API are reachable at all. Still worth a look if the compiler complains: switch expressions in `Models.swift` and the views (valid Swift 5.9+, need Xcode 15), `@Observable` on the `NSObject` subclass `RelayService`, and Sendable warnings around `AppDelegate`.
2. **Run against real NWS.** Set the User-Agent, pick a festival, confirm alerts and hourly decode. Check a real alert with `ends: null` (the fixture in `backend/test/fixtures/nws.js` covers it, reality may differ).
3. **Radar against the real archive.** Start the backend for an in-window festival, watch `radar/<id>/` fill (72 frames, newest first), open a frame, then open the Radar screen and check the echoes sit where the map says they should (Mercator on both sides, so a misalignment means a bbox bug). Confirm the 10-minute lag is enough for the newest timestamp to exist on the IEM side; if frames often 404, raise `LAG_MS`. Check the phone's offline path: airplane mode, reopen Radar, the saved loop should play.
4. **Backend: first real run.** Deployed on Railway at `https://fieldwatch-production.up.railway.app` and baked into `web/index.html` and `ios/project.yml`; the web build is on GitHub Pages. Still to check on the live service: the log lines from the first NWS poll and radar fetch (nothing in this project has hit either for real before), a `TICKETMASTER_KEY` and the first import report (`POST /admin/import`), and a tile provider with a usage agreement before real traffic.
5. **Push end to end.** Web push is done (`backend/src/webpush.js`, the switch on the web build's home screen); the first real send needs VAPID keys on Railway (`npm run vapid`) and a phone with the site on its Home Screen. APNs for the iOS app still needs a key, device registration, and tap-to-open into `AlertDetailView` with no network.
6. **Relay test on two devices.** Airplane mode on one, Bluetooth on, warning triggered on the other.
7. **Receiver node on real hardware.** Pi 5 + RTL-SDR V4, one county P25 system from RadioReference. Measure Whisper latency (target under 60 s per call on a Pi 5). Confirm Bonjour discovery from an iPhone on the hotspot. Check that the uploader can delete what trunk-recorder (root, in Docker) wrote: `setup.sh` sets a default ACL on `recordings/` for this and the uploader logs one clear line if it can't; neither has been tried on a Pi.
8. **Hazard rules against real traffic.** `fire` matches any call that says "fire", which on a fire/EMS dispatch talkgroup is most of them; `redact()` turns road names like "CR 136" into `[plate]`. Tune against a day of recordings, and add each decision to `backend/test/fixtures/hazard-samples.json`.
9. **Moderation UI for incidents.** Festival suggestions have a review screen in the web build (Settings, admin key), and attendees can now send hazard reports from the web build. Approving reports and node incidents still only has the queue endpoints; the same review screen pattern fits.
10. **Festival official dashboard.** Same: a web page that hits `POST /festivals/:id/posts`.
11. **Offline map in the pack.** Medical, water, exits, harm reduction. Needs real site data from each festival; the schema (`SiteItem`) exists.
12. **Pack downloads with a map tile bundle.** Optional; the prototype promises "site map" and the pack doesn't carry one yet.
13. **App Store review notes.** Explain the Bonjour service, local network permission, background audio, and that scanner content is public-safety radio only. Drop `fetch` from `UIBackgroundModes` and the location usage string unless something starts using them.

14. **More festival sources.** SeatGeek and Edmtrain importers exist beside Ticketmaster's (`backend/src/importers/`); none of the three has been run against the live API from this project yet, so the first run with real keys should be watched (`POST /admin/import` starts one; `GET /admin/import` or the `imports:` log line has the report). Wikidata is in (`wikidata.js`, no key, on by default): two cheap SPARQL queries (every kind of festival, then the US items of those kinds with coordinates; one property-path query timed out on the live service), and this year's dates read from each festival's own site's schema.org JSON-LD, politely and cached; it has not run against the live endpoint or a real site from here either. Still open: JamBase (paid after a trial, best for the jam and camping scene) and Bandsintown for lineups. And a `groundsOpen` date on the curated records that have long builds.

Explicitly out of scope: any attempt to receive RF on the phone, Broadcastify integration, recording festival ops radio without consent, accounts.
