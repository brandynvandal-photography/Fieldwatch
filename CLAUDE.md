# Fieldwatch

Festival safety-alert app. iPhone-only for users, no accounts, offline-first. Pick a festival, get channels: Weather (alerts, hourly forecast, a 12-hour radar loop), Festival official, Incidents, Attendee relay, Live audio (where a feed exists). "Fieldwatch" is a working name.

This repo was scaffolded in a chat session on a phone, then worked over in a Claude Code cloud session that had no Xcode. **The Swift has still never been compiled.** It has been read line by line for compile errors (see `docs/roadmap.md`, item 1, for what was fixed and what to expect), but the first job on a Mac is still: generate the Xcode project, build, and fix whatever the compiler finds. The backend and node run and have test suites.

## Commands

```
# backend
cd backend && npm install && npm start   # seeds itself; prints the admin key once; .env only to change something
curl localhost:3000/festivals
npm test                      # node:test, no network: api.weather.gov is a fixture

# ios (needs macOS + Xcode 15+)
brew install xcodegen
cd ios && xcodegen generate && open Fieldwatch.xcodeproj

# node (on a Pi; on a dev machine you can run uploader.py directly)
cd node && cp node.env.example node.env && python3 uploader.py
python3 test_uploader.py      # stdlib only; whisper is stubbed, the backend is a fake server

# web
cd web && npm start           # http://localhost:8090; any static host works
npm install && npm test       # headless Chromium against fixture NWS and radar responses

# both suites run in GitHub Actions on every push (.github/workflows/ci.yml); contract.yml checks the outside services nightly
node backend/scripts/contract.mjs [https://backend]   # the weather service, a lightning bucket, the radar archive, in the shapes we parse
```

`backend/.env` is read by `src/env.js` (Node 20.12+, `process.loadEnvFile`); variables already in the environment win. `npm start` runs `src/server.js`, which is only the listener; the Express app lives in `src/app.js` so tests can import it without binding a port.

## Architecture in one paragraph

The phone downloads a **festival pack** (`FestivalPack`: festival, alerts, posts, hourly forecast, incidents) once and works from disk after that. While online it polls the backend for alerts/posts/incidents and NWS directly for the hourly forecast, and falls back to NWS directly for alerts if the backend is down. The backend polls NWS every 30 seconds for every festival that is on (grounds open, a week before gates or `groundsOpen`, to 1 day after the end), by the festival's county and forecast zone, keeping the alerts whose polygon reaches the grounds and the zone-wide ones (`nws.js` `alertsFor`; a point query misses a polygon drawn across a large site's edge), one message per warning (`condense`: an update replaces what it references and is not pushed again, a zone segment counts only where it names the grounds' own zone or county, one event with one end is listed once; the web build condenses what it holds the same way, `condenseAlerts`), stores them, and pushes new ones over APNs with the full alert JSON in the payload so the detail screen opens offline, and over Web Push (`webpush.js`, VAPID) to every browser that favorited the festival (one `web_subscriptions` row per phone per festival, the spot a phone follows as `here`), with a link that opens the web build on that alert; the push opens with the line to act on (`actionLines`, in the shared block), and when the warning ends or a lightning code lifts a quiet push under the same tag says so (`pushEnded`, `liftWords`). It also reads each live festival's hourly forecast and grid every 20 minutes and, up to `HEADS_UP_HOURS` before the forecast turns stormy, windy, wet or dangerously hot, stores and pushes a **heads-up** of its own (`incoming.js`, channel `headsup`, one per window, never for a hazard whose warning is already in effect) with the time it starts and what to do first, for storms, wind past what is standing (with the side it comes from and how sure, `gustOdds`, `dirWords`), rain and the mud it makes, rain hard enough to flood, dangerous heat and a cold night (`THRESHOLDS`); the stored heads-up follows the forecast when the window moves and is withdrawn when the forecast lets go (`headsUp` in `poller.js`), a second window later in the twelve hours is named (`next`), and a window that comes while people sleep gets the before-you-turn-in line (`timing` with the local hour); the web build shows the same thing as a countdown card under the sky and a prep screen (shelter, camp, timeline, what to pack). **Lightning** (`lightning.js`) reads the GOES lightning mapper's 20-second files from NOAA's public S3 buckets every 20 seconds while a festival is on (h5wasm reads the NetCDF-4 in Node) and grades each festival on the festival safety protocol by the nearest flash: red under 8 miles (rapid evacuation, full work stoppage; all clear 30 minutes after the last close flash), orange 8 to 12 (evacuation procedures, staff hold posts), yellow 12 to 20 (prepare), green beyond. A change to orange or red is pushed as an alert (channel `lightning`, the protocol's own wording, kept in `PROTOCOL` in `lightning.js` and `CODE` in the web build), and the web build shows the code on the lightning tile under the festival page's sky card (not beside the title), beside every festival's name on the home page's cards, and on a screen of its own, always the higher of the live grade and a red or orange alert still standing (`lightningState`), so the sky card and the tile under it never contradict each other. Every change (an alert landing or ending, a heads-up, a lightning code, a post, a ground report) is announced on the **live stream** (`live.js`, `GET /events`, server-sent events); the web build holds one open and refreshes just the festival or the feed that changed, so an open page moves within a second of the backend on top of its own polls. Phones relay warning-level alerts to each other over MultipeerConnectivity (`RelayService`). A **receiver node** on site records county public-safety radio, transcribes, keeps only hazard traffic, serves it on its own Wi-Fi (`_fieldwatch-node._tcp` over Bonjour) and uploads to the backend. Pairing a phone with the node is joining its Wi-Fi; `NodeDiscovery` does the rest. Both the backend and the node are plain http on a local network, so `project.yml` sets `NSAllowsLocalNetworking`. **The web build** (`web/index.html`) is the same app for a browser: it reads `festivals.json` and then the backend's live list when one is set, asks NWS and the radar archive directly (or a backend when one is configured, with NWS as the fallback) and caches everything in the browser (`save` keeps the chosen festival, the favorites and your own spot, survives a full store, and Diagnostics says when it could not; the service worker keeps the shell, the radar frames and tiles it has seen, and the alert each push carries, so the loop and the alert screen work with no signal). **Radar** (`backend/src/radar.js`) fetches one NEXRAD composite image per 10 minutes for the last 12 hours from the Iowa Environmental Mesonet WMS-T archive, for a fixed Web Mercator square around each in-window festival, caches the frames on disk (they never change) and serves a manifest plus the PNGs; the phone (`RadarStore`, `RadarView`) keeps the frames on disk and draws them as an `MKOverlay` on MapKit, so the last loop plays offline.

## Shared data shapes

`Festival` records come from `backend/src/festivals.js` (`normalizeFestival`), whatever the source: the curated seed, the Ticketmaster, SeatGeek and Edmtrain APIs, Wikidata plus each festival site's schema.org JSON-LD (`backend/src/importers/wikidata.js`, a polite crawler: robots.txt honored, redirects followed by hand, public DNS names only, on from the first boot since the User-Agent names the app's page), feed URLs and community suggestions. `SafetyAlert`, `Incident` and `RadarLoop` are defined in `ios/Fieldwatch/Models/Models.swift` and produced by `backend/src/nws.js`, `backend/src/app.js` (`incidentToAlert`), `backend/src/radar.js` (`radarLoop`) and `node/uploader.py`. `web/index.html` consumes all three and re-implements the NWS normalizer and the radar square; change them in step. The weather logic (thresholds, the grid spread, `incoming`, the prep tables) is one block between `// ==== shared: start ====` and `// ==== shared: end ====` in `backend/src/incoming.js`, copied byte for byte into `web/index.html`; `backend/test/mirror.test.js` fails when the two differ, so edit the backend's and paste the block across. Pure functions only in that block: nothing from the page or the server. Keep them in sync by hand; there's no codegen. Dates are ISO 8601; the Swift decoder accepts with or without fractional seconds, the backend emits without (`util.js: iso()`).

Hazard categories live in two places on purpose (node must classify offline): `backend/src/incidents.js` and the `CATEGORIES` list in `node/uploader.py`. Change both, and add a line to `backend/test/fixtures/hazard-samples.json`; both test suites run every sample through their own classifier, so a drift fails one of them.

## Rules that are not up for debate

- Nothing to set up to run. Every variable in `backend/.env.example` is optional: the admin key and the web push keys are made on the first boot and kept in the database (`adminkey.js`, `webpush.js`; the admin key printed once, `ADMIN_KEY` in the environment wins), the User-Agent to every service defaults to the app's own page (`site.js`, `USER_AGENT`), the data follows the volume, and every source read is free and keyless. A feature that needs a token stays optional and says so in `/health` and `.env.example`.
- No accounts, no login, no analytics that identify a person. Phones register only an APNs token + festival id. A festival's staff key (`POST /festivals/:id/partner-key`, kept hashed, shown once, with a handoff link and QR that put it on a staff phone in one scan) is the festival's, not a person's: it works for that festival's posts, moderation, ground and record, and for nothing admin-wide (`requireStaff`; the web build asks `/staff/me` what a key is and hides the rest, `canStaff`, `adminScope`).
- The receiver node records **county public-safety radio only**. Never the festival's operations channels without the promoter's written OK. See `docs/decisions.md`.
- Do not integrate Broadcastify. They are not licensing new scanner-style mobile apps.
- Only hazard traffic is stored. Non-matching calls are deleted, audio included. Redaction (`redact()`) runs before storage.
- Attendee reports always go through the moderation queue. Never auto-publish them.
- No festival name, coordinates or date goes into `backend/data/festivals.json` without a `source` URL. Coordinates must be the grounds, not the town. `backend/data/grounds.json` is the list of known grounds (pin, county, camping, indoor, source; `verifiedOn` null until someone has checked the pin on a map): an import or a suggestion within a kilometer of known grounds, or within three when it names them, takes the grounds' pin and facts (`grounds.js` `snapToGrounds`), and staff can move a festival's pin to where they stand from the Ground screen. Imported and suggested festivals carry their source URL too, and never overwrite a curated record.
- Only festivals that are on are listed, polled and watched: grounds open (a week before gates, or `groundsOpen`) through the day after the end. `isLive` in `backend/src/festivals.js` and `web/index.html` must agree.

## Conventions

- Swift: iOS 17, `@Observable`, one `AppState` as source of truth, views read from it, `Route` enum for navigation. No third-party packages so far. Anything an `@Observable` class mutates off the main thread, or declares `lazy`, is marked `@ObservationIgnored`.
- Backend: ESM, no build step, prepared statements in `db.js` only, all env in `.env.example`, async routes wrapped so a rejected promise becomes a JSON 500 instead of a crash. Tests are `node:test` in `backend/test/`.
- Node: one file, stdlib plus faster-whisper. Anything that must be testable without hardware is a function (`process_call`, `upload_once`), and the loops just call them.
- Copy in the UI is sentence case, plain, short. The prototype has the reference wording for every screen. One exception: a lightning code is a proper name with both words capitalized, Code Red, Code Orange, Code Yellow, Code Green, in labels, alert events and pushes alike.
- Airy, and in the theme, whatever the text: long text is never squeezed into a narrow column beside a label. It stacks under a small uppercase label (`.sec`, `.tl`) at reading size with room under it, bullets become their own short paragraphs (`bullets`), long lists are cut short with "and N more" (`areaText`), and anything scrolled fades under the top bar rather than colliding with the clock. Two-column rows (`.kv`) are for values that fit on a line or two. A row of choices (`.chips`) is one line per section, the chips sharing the row equally like a segmented control, never wrapping: a label that does not fit six across a phone gets a short form for the chip (`SURFACE_CHIP`, `SOIL_CHIP`, `STRUCTURE_CHIP`) while the readouts keep the longer word, and the web test checks no chip is cut short.
- Indoors is its own place: a club, a hall or an arena (`indoor` on the record: staff, a building under the coordinate in OpenStreetMap, or the venue's words) gets no lightning code and no code alert, no wind, heat or rain heads-up, and inside-is-shelter advice for storms and flooding; unknown counts as outdoors. Indoors needs every source that speaks to agree (`effectiveGround`): mapped open ground under the pin, a park, a farm or a mountain in the listing, or people camping here each say outdoors and beat a building under the pin, because an imported pin often sits on the lodge or the box office of open grounds, and out is the safe side; a stadium, a pavilion, an amphitheater or an events venue with no building is no roof (`indoorFromTags`). Staff keep the last word. The web build says Indoors on the tile, the lightning screen and the home page card. The flashes behind a code are a route of their own (`/festivals/:id/lightning/flashes`) and dots on the radar square (`flashDots`), inside the protocol's rings (`rings`); where they are going is `motion` on the grade (`motionOf`) and a badge on the square (`arrivalBadge`). Your own spot is graded through `/point/:lat,:lon/lightning` (`lightningAt`: asked about, kept in the reader's reach for a day, a warm-up first).
- Advice fits the person and the place: tent, canopy and camp advice only where people camp (`camping` on the record: seed, staff, OpenStreetMap campground, a camping pass on sale), a day visitor's list where they do not or nobody knows, crew's where things stand; the phone never hands anyone a form: it reads the setup from the record (people camp here, or not) and the prep screen's heading carries one small link, Not camping?, that opens the choice (`setupHead`, `S.setupOpen`). Nobody is told to move the car to hard ground as if they could: campers get the if-you-still-can line, day visitors the leave-before-or-wait-it-out line.
- Motion belongs to a move: the screen's entrance animation runs once per navigation (`render` keys on screen and param). Every other render, and there are dozens (data landing, a busy flag, a keystroke, a live change), swaps the same screen's content in place, with no rise or fade, and keeps an opened fold open. The display font loads with `display=optional` so its arrival never reflows a title; the service worker caches it, so it is there from the second open on. The web test counts `rise` animation starts. A text box is never rebuilt while someone types in it: the picker's search redraws only the list under the box (`filterFests`, `pickerBody`), so the caret, the keyboard and its autocorrect state stay where they were; the box has autocorrect off, since a festival name is not a word.
- Only what matters is on screen. The festival page is the sky, the code, the heads-up with its first step, and three orbs; rows appear only for what is there (a partner's updates, a backend's incidents and reports). The weather screen is alerts and the forecast. On the lightning screen the current code stands in full and the other three fold away; on the prep screen the timeline and the pack list fold away. An alert ends with its area and source. The carrier-alert line lives in Settings.
- The safety team's calls are posts with a `kind`: a notice, or a hold (shelter, evacuate, pause) with an end that stands on the festival page in its own color until the all-clear ends it (`HOLD_ACTION` in the shared block, `TEMPLATES` on the Post screen); every post keeps its reach and can be taken back, quietly, under the same tag. Shelter and medical live on the record in the team's words (`shelter`, `medical`) and ride on every warning, hold and prep screen.
- Panic first: someone opening an alert may read one line and nothing else. Every alert opens with one imperative under eight words and one line of what not to do (`ACTION`, `actionLines` in the shared block; `actionFor` in the web build reads them for this festival's setup), the same two lines a push opens with; a warning that lands while the page is open takes the screen with them (`takeover`), and a warning that ended stays on the sky card for half an hour with what to do now rather than vanishing (`endedRecently`), then the time left as a number; the weather service's own text folds away under "Full alert". Numbers and countdowns beat sentences; a screen for a calm moment (prep, the codes) may explain, a screen for a warning may not.
- American English everywhere: copy, comments, docs and tests (color, center, meters, canceled, gray). The only British spellings left are values that mirror an outside API (a Ticketmaster status code) and a regex that matches venue names spelled either way.
- The Ground screen's chips are what the lookups found, selected on their own: they start fresh on every visit and follow ground that lands while the screen is open, until staff touch one (`S.groundDirty`). Staff correct; they do not have to pick. The readout is the screen; the six rows of chips wait behind one Correct it fold, and the screen itself is reached only with the admin key (the festival page's Ground row). The public is never asked to pick anything about the grounds: its one tap is the ground report (Fine, Soft, Mud, Water), shown only when rain is in the picture.
- A festival is listed once, whatever the ticket sites call it. A listing that shares grounds on overlapping dates with another source's record, or shares its name within 8 km (`sameFestival`; the same core or its nickname, initials like ACL for Austin City Limits or the front of the word like Lolla, `sameCore`), is a duplicate and is skipped; a late-night show or an aftershow sold under the festival's name is an add-on, dropped like parking (`ADD_ON`); and a stored import that a source ahead of it holds (curated, suggested and feed records, then Ticketmaster, SeatGeek, Edmtrain and Wikidata, the run order) is removed on its source's next run (`applyImport`). When a duplicate shows up on the home page, teach the matcher; hiding it by hand is the last resort.
- The home page is one place: the festival you are standing at (within `NEAR_KM`), else the weather where you stand (`locate`, `goHere`); without a location it is the festivals list. Every other festival waits behind the Festivals button: the list (`screens.feed`) is every festival that is on, organized by lightning code with red at the top (`CODE_ORDER`), the worst alert then the nearest within a code, favorites wearing their heart, a favorite not on yet last with when it opens. Code Green and Indoors are one bubble each (`codeFold`, `FOLDS`), the bubble also the group's header: every festival of that group starts inside it, warnings included, counted on its line with the advisories and a red bar when a warning is inside, the line full width under the title row, opened with a tap; red, orange, yellow and the no-data group stay open. Search is one row further (`screens.picker`).
- The first open is a walkthrough (`screens.welcome`, `WALK`): the intro scene as its cover (a sun up, clouds in, one bolt, the name; the base CSS is the final frame, so motion off shows the cover plain), three pages that teach (the sky card, the lightning code, radar and forecast and prep), and a start page with Use my location or I'll pick a festival. Picking a festival is not a location denial (`geoSkip`): the app stops asking on its own and asks again when a location row is tapped; `geoDenied` is only the browser's no. The first festival page gets the tour (`TOUR`, `tourStart`): a spotlight per element with a card that says what it is, Next through to Done, a step skipped when its element is not there. Both run once (`welcomed`, `toured`) and replay from Settings. The web tests take the tour as done for every page but the walkthrough's own test.
- The phone's own back works: every `go` is a history entry (`pushHistory`) and the Back button goes through the browser (`back` → `history.back()` → `popScreen`), so the stack and the history never disagree; a redraw in place keeps focus where it was (`render` finds it again by its place); a warning landing, a code moving and the thunder clock are said to a screen reader (`announce`, `#live`); every row says its severity in a word beside its color (`alertSub`); Sun mode, text size and the battery saver are `data-theme`, `data-text` and `data-saver` on the root (`applyPrefs`), kept across opens.
- The safety team's code never lowers the mapper's: `PUT /festivals/:id/lightning` confirms or raises the grade for a bounded time and `lightningFor` shows the higher of the two with `staff` beside it; the page says set by staff wherever the code shows, and the record keeps the set and the release (`lightning-staff` rows). A release hands the grade back; it does not call an all-clear.
- Spanish is a layer over the lines people act on, never a second copy of the page: `T` looks a line up in `ES` (web) and returns the English when nothing is there, so a line is never blank and the shared block stays in one language; the weather service's own words are never translated. Add to `ES` when a line people act on changes; do not translate the staff screens or the diagnostics.
- The radar square says only what it draws: the warning's own area, the flashes, the storm reports and your dot appear when they exist, and the one line under the square (`radarKey`) names only those.
- Emergency alerts from carriers (WEA) are not something we replace; the UI tells users to keep them on.
- The public sees no plumbing: the backend address, its check and the admin key stay out of Settings until five taps on the credits line, `?staff=1`, `?backend=`, or a saved key (`staffMode` in the web build). A favorite is a festival whose warnings reach this phone (`toggleFavorite`, `follow`, `unfollow`, `ensurePush` re-registers every favorite once an hour on open); the favorite is offered once, on the festival page right after it is picked (`askPush`), and never nagged about again.

## Things to verify early

1. The User-Agent to the weather service is `Fieldwatch/<version> (+the site address)` unless `NWS_USER_AGENT` is set (`backend/src/site.js`; `NWSClient.userAgent` carries the same). Nobody has hit the real API from this code yet: the cloud session's network policy blocked api.weather.gov, so the normalizer is only proven against a fixture, and the first live call also confirms the service takes a website as the contact (its documentation says it does).
2. Festival names, venues and dates in `backend/data/festivals.json` were confirmed against each festival's own site on 2026-09-27 (`source`, `verifiedOn`). Coordinates are venue centroids typed from memory; drop a pin on each before relying on polygon-based NWS alerts.
3. `web/festivals.json` is a copy of that file; a backend test fails if they differ.
4. `project.yml` bundle id prefix. `FieldwatchBackendURL` is the Railway deployment; the web build's `DEFAULT_BACKEND` is the same address. The `aps-environment` entitlement needs a paid team; on a free team, delete the `entitlements:` block to build to a device (the simulator doesn't care).
5. APNs needs a paid developer account; until then the in-app banner covers the demo. The server starts fine without the keys.
7. Lightning has never read a real GLM file either (same network policy): `backend/test/lightning.test.js` writes files the way NOAA lays them out (with h5wasm) and the reader is proven on those. The first live run should confirm the bucket names (`noaa-goes19` for GOES-East since April 2025, `noaa-goes18` for West; `/health` shows `lightning.buckets[].lastError`), that a real file's `flash_lat`, `flash_lon` and `flash_time_offset_of_first_event` unpack to sane values (a flash should land within a few minutes of its file's start time), and how many flashes an active day keeps in the buffer.
8. The ground lookups have never run live either: Overpass (`is_in`, then `around:250` with `out center`), the MRLC land cover WMS (`GetFeatureInfo`, `INFO_FORMAT=application/json`, the class in `GRAY_INDEX` or `PALETTE_INDEX`; the layer name `NLCD_2021_Land_Cover_L48` is from memory and `NLCD_LAYER` changes it), the USDA Soil Data Access query (`SDA_Get_Mukey_from_intersection_with_WktWgs84`, `format: JSON+COLUMNNAME`) and the Mesonet `iemre/multiday` point service are written from their documentation and proven against fakes in `backend/test/ground.test.js`. On Railway, with a festival on, watch the `ground:` log line, `/health` → `ground`, and a record's `/festivals/:id/ground` for `lookupError` or `pastError`; a wrong response shape shows there first.
9. The nowcast (`backend/src/nowcast.js`) is proven on frames drawn by hand, not the archive's: the first real frames should confirm that rain is colored and the rest transparent as `echoMask` assumes (a legend or a label drawn in color would count as echo), that the motion it finds matches what the loop shows, and that the arrival is not silly; `/festivals/:id/nowcast` for a featured festival with weather nearby is the check.
10. The live stream and the zone alerts have run only against the test client: on Railway, open `/events` in a browser tab (or `curl -N`) and confirm it stays open through the proxy with a `: ping` every 25 s and a `change` line when a post goes out; and watch the first `alerts/active?zone=` answers (`/points` must name `county` and `forecastZone`; a polygon warning near a festival should land, a far one should not).
6. Radar has never been fetched from the real archive by this code either (same network policy). The WMS parameters (`n0q-t.cgi`, layer `nexrad-n0q-wmst`, `EPSG:3857`, `TIME=`) follow the IEM documentation; the first real run should confirm a frame decodes and lines up with the map, and that a 10-minute lag is enough for the newest timestamp to exist.
